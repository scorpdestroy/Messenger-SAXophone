# Спринт 2: контракт и сценарии пользователей

Подготовлено 27.10.2026 по локальному срезу карточек Pyrus от 27.10.2026.
Документ описывает реализованный код. Согласование командой отдельно не подтверждено.

## Сценарии

1. Регистрация: гость вводит логин, почту, пароль и необязательное отображаемое имя.
   При успехе получает подтверждение и переходит на вход. Сессия автоматически не создаётся.
   Неверные поля дают 400, занятый логин или почта — 409. При ошибке форма сохраняет введённое.
2. Вход: пользователь вводит логин либо почту и пароль. Успех открывает профиль.
   Ошибка 401 одинаковая для неизвестного аккаунта и неверного пароля; сетевую ошибку можно повторить.
3. Профиль: гость перенаправляется на вход; авторизованный пользователь видит имя, логин и почту.
   При refresh показывается загрузка и запрашивается `/users/me`. Ошибка сети имеет кнопку повтора.
   При 401 сессия очищается и открывается вход, без автоматического повторения запроса.
4. Выход: сервер отзывает текущую сессию, клиент удаляет токен и открывает вход.
   При сетевой ошибке клиент сохраняет сессию и предлагает повторить выход.
   Другие сессии этого пользователя остаются действительными.

## HTTP API

В браузере адреса начинаются с `/api`; Nginx/Vite убирает этот префикс.

| Метод и маршрут backend | Запрос | Ответ |
|---|---|---|
| POST /auth/register | username, email, password, display_name? | 201 UserPublic; 400; 409 |
| POST /auth/login | identity, password | 200 access_token, token_type, expires_in, user; 400; 401 |
| POST /auth/logout | Bearer access token | 204 без тела; 401 |
| GET /users/me | Bearer access token | 200 UserPublic; 401 |
| GET /users?query=bob&limit=20 | Bearer access token | 200 массив UserSummary; 400; 401 |

Регистрация:

```json
{"username":"alice","email":"alice@example.test","password":"Example-only-password-123","display_name":"Алиса"}
```

Вход:

```json
{"identity":"alice@example.test","password":"Example-only-password-123"}
```

`UserPublic` содержит только `id`, `username`, `email`, `display_name`.
`UserSummary` содержит `id`, `username`, `display_name`; поиск не раскрывает почту.
Идентификаторы — строки UUID. `expires_in` — секунды, `token_type` — `bearer`.
Заголовок защищённых запросов: `Authorization: Bearer <access_token>`.
Токен и пароль не включаются в ответы профиля/поиска. Login и профиль возвращают `Cache-Control: no-store`.

Ошибки: `{"error":{"code":"http_409","message":"Username or email already registered"}}`.
Для неверного тела/параметров auth/users: 400 с `code=validation_error`, без отражения входного пароля.
401 имеет заголовок `WWW-Authenticate: Bearer`. Неожиданная ошибка — 500 без SQL/секретов в ответе.

## Проверки полей и поиск

- Логин: обрезаются внешние пробелы, приводится к нижнему регистру; 3–32 латинских буквы, цифры, `_`.
- Почта: внешние пробелы удаляются, регистр понижается; до 254 символов, адрес с доменом и точкой.
- Пароль: 10–128 символов при регистрации; не обрезается и не приводится к другому регистру.
- Отображаемое имя: до 80 символов после trim; пустое заменяется логином.
- БД обеспечивает уникальность логина и почты без учёта регистра, включая конкурентные регистрации.
- Поиск работает по подстроке логина/имени, без учёта регистра, исключает текущего пользователя.
  Пустой запрос возвращает пустой массив; длина query до 80, limit 1–50 (по умолчанию 20).
  `%` и `_` ищутся буквально. Порядок: логин, UUID. Это API пользователей; UI поиска относится к S3.

## Сессия и хранение

Пароли хешируются scrypt с отдельной случайной солью, N=32768, r=8, p=1.
Сравнение хеша выполняется через constant-time compare. В БД нет открытого пароля.
JWT подписывается HS256; проверяются подпись, алгоритм, exp, iat, iss, aud, sub и jti.
UUID jti связан с `auth_sessions`; отсутствие, истечение или удаление записи делает токен недействительным.
Logout отзывает сессию на сервере. Полноценного refresh token нет: после истечения требуется новый вход.

Клиент хранит access token в sessionStorage своей вкладки, пароль туда не записывается.
Обновление страницы восстанавливает сессию; закрытие вкладки завершает клиентское хранение.
App.tsx хранит текущего пользователя в обычном state; запрос 401 очищает клиентскую сессию.

## Запуск, окружение и demo seed

`.env.example` содержит все настройки приложения. Pyrus-ключи к приложению не относятся.
`AUTH_SECRET_KEY`: сгенерировать `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
Ключ не коммитить. В production обязательны минимум 32 байта; пустой/короткий ключ не запускает приложение.
В development/test без ключа создаётся временный ключ процесса: перезапуск завершит старые сессии.
Для сохранения сессий после перезапуска задайте постоянный локальный ключ в `.env`.
`ACCESS_TOKEN_MINUTES`: 1–1440, по умолчанию 60.

Для отдельного S2-окружения здесь заданы локальные порты 8081, 8001, 55433:

```powershell
docker compose -p messenger-s2 up --build --wait
```

На чистой копии сначала заполнить `.env` по примеру; для параллельного S1/S2 задать
`FRONTEND_PORT=8081`, `BACKEND_PORT=8001`, `POSTGRES_PORT=55433`.
Именованный volume привязан к имени Compose-проекта. Обычный restart/down сохраняет данные.
Удаление volume удаляет БД; для одноразовых тестовых окружений это допустимо.

Seed запускается явно, при старте сервера demo-пользователи не создаются:

```powershell
# Задать свой DEMO_PASSWORD длиной 10–128 символов в переменной окружения терминала.
docker compose -p messenger-s2 exec -T -e DEMO_PASSWORD backend python -m app.seed
```

Команда использует DEMO_PASSWORD из окружения вызывающего терминала, а не автоматически из .env Compose.
Пользователи: demo_alice и demo_bob, адреса `<username>@example.test`.
Повтор не создаёт дубликаты и не меняет существующие пароли. Команда также удаляет истёкшие сессии.

## Проверки

- Backend: `ruff check .`, `ruff format --check .`, `python -m pytest -q` из backend.
- С `RUN_DB_TESTS=1` и `DATABASE_URL` отдельной мигрированной PostgreSQL все API-тесты
  используют транзакции с откатом. Базу приложения для миграционного rollback-теста не использовать.
- Frontend: `npm run lint`, `npm test`, `npm run build` из frontend.
- Полный браузерный сценарий: задать `E2E_BASE_URL=http://localhost:8081`, `E2E_API=1`,
  выполнить `npm run test:e2e`. Без E2E_API выполняются только гостевые маршруты, auth-тесты явно skipped.
- CI: отдельная чистая PostgreSQL, миграции, API-тесты, rollback/upgrade; отдельный Compose job
  проверяет реальный auth-поток через Nginx. При UI-сбое сохраняются screenshot и trace в artifact.
  GitHub-hosted окружения одноразовые; Compose job явно удаляет свои контейнеры и volume.

Источники решений: [PyJWT](https://pyjwt.readthedocs.io/en/latest/usage.html),
[hashlib.scrypt](https://docs.python.org/3/library/hashlib.html#hashlib.scrypt).

Карта текущих файлов после упрощения: [structure.md](structure.md). Маршруты находятся в auth.py, операции пользователей — в users.py, состояние клиента — в App.tsx.
