# Руководство по стилю кода

## Вариант 1. Стандарты, условия, DRY/KISS и базы данных

Правила относятся к серверу на Python и FastAPI с SQLAlchemy и клиенту на TypeScript и React. Примеры показывают рекомендуемый стиль; их не нужно вставлять в проект без учёта задачи.

### 1. Стандарты и принципы стиля кодирования

- Пишем код так, чтобы его мог прочитать и изменить другой участник команды. В пределах файла соблюдаем единый стиль.
- Для Python используем соглашения PEP 8: отступ в четыре пробела, `snake_case` для функций и переменных, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант. Длинные выражения переносим внутри скобок.
- В TypeScript и TSX используем отступ в два пробела, `camelCase` для переменных и функций, `PascalCase` для типов и компонентов. Как в существующем клиенте, используем одинарные кавычки и опускаем необязательные точки с запятой.
- Не смешиваем табуляцию и пробелы. Сохраняем файлы в UTF-8, удаляем пробелы в конце строк и оставляем перевод строки в конце файла.
- Импорты Python группируем: стандартная библиотека, сторонние пакеты, модули проекта. Между группами оставляем пустую строку; не используем `import *`.
- Для новых и изменяемых функций указываем типы параметров и результата. Не скрываем неизвестный тип за `any`, если можно описать его явно.
- Комментарий объясняет причину решения или ограничение, а не пересказывает строку кода. Удаляем закомментированный устаревший код.
- Перед передачей изменений на проверку запускаем предусмотренные проектом проверки. Для клиента это `npm run lint` и `npm run build` из каталога `frontend`. Единый форматтер для Python сначала согласуем с командой, затем добавляем его настройки в репозиторий.

### 2. Логические операторы и условия

- В Python используем `and`, `or`, `not`, в TypeScript — `&&`, `||`, `!`. В TypeScript сравниваем значения через `===` и `!==`.
- Проверяем отсутствие значения явно: `value is None` в Python; `value === null` или `value === undefined` в TypeScript. Не подменяем такой проверкой проверку пустой строки или нуля.
- При смешении `and` и `or` выделяем смысловые группы скобками. Сложное условие разбиваем на переменные с понятными именами.
- Используем ранний выход или исключение для недопустимого случая, чтобы основной сценарий не оказался внутри нескольких вложенных `if`.
- Не сравниваем логическое значение с `True` или `False`. Избегаем двойных отрицаний и вложенных тернарных выражений.
- Учитываем короткое замыкание: правый операнд может не выполниться. Не помещаем обязательную запись в БД или другое обязательное действие внутрь логического выражения.

Пример проверки текста сообщения:

```python
def validate_message_body(body: str | None) -> str:
    if body is None:
        raise ValueError("Message body is required")

    normalized_body = body.strip()
    if not normalized_body or len(normalized_body) > 4000:
        raise ValueError("Message body must contain 1 to 4000 characters")

    return normalized_body
```

В TypeScript `value || fallback` заменяет также `0`, `false` и пустую строку. Когда значение по умолчанию нужно только для `null` и `undefined`, используем `value ?? fallback`.

### 3. Принципы DRY и KISS

DRY означает, что одно правило или одна операция имеют одно место реализации. KISS означает, что выбираем самое простое решение, которое выполняет требования.

- Повторяющуюся проверку или операцию выносим в общую функцию, если у повторений один смысл и одна причина изменения.
- Для HTTP-запросов клиента используем общий `request` из `frontend/src/api.ts`, для хеширования паролей — функции из `backend/app/secure.py`, для получения сессии БД — `get_db`.
- Не копируем запросы поиска пользователя по обработчикам: используем функции из `backend/app/users/repository.py`.
- Повторяющиеся ограничения называем константами с понятным назначением. Если ограничение необходимо и клиенту, и серверу, согласуем его в контракте; сервер всегда проверяет его независимо от клиента.
- Не объединяем похожие по записи операции, если у них разные правила. Не создаём универсальный класс с множеством переключателей ради устранения нескольких строк.
- Предпочитаем обычные условия и небольшие функции сложным цепочкам выражений. Не добавляем паттерны и зависимости без текущей потребности.
- При выделении общей функции проверяем все места её вызова, чтобы исправление одного сценария не сломало остальные.

### 4. Работа с базами данных и запросами

- Используем SQLAlchemy и сессию `Session`, полученную через `Depends(get_db)`. Не создаём новое подключение в каждом обработчике и не разделяем одну сессию между параллельными запросами.
- Запросы к пользователям размещаем в `backend/app/users/repository.py`, а последовательность действий регистрации и управление её транзакцией — в `backend/app/users/service.py`.
- Передаём пользовательские значения как параметры SQLAlchemy. Не собираем SQL через f-строки, конкатенацию или подстановку пользовательского текста в `text()`.

Пример параметризованного запроса:

```python
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models import User


def find_user_by_username(db: Session, username: str) -> User | None:
    return db.scalar(select(User).where(User.username == username))
```

- Проверяем входные данные до записи. Уникальность, внешние ключи и другие обязательные ограничения закрепляем также в БД: предварительная проверка не защищает от одновременных запросов.
- Связанные изменения выполняем в одной транзакции. Функция, управляющая операцией, вызывает `commit()` после всех изменений; при ошибке выполняет `rollback()` перед дальнейшей работой с сессией. Не делаем скрытый `commit()` внутри вспомогательного запроса.
- Ожидаемые конфликты ограничений переводим в понятную ошибку приложения. Не считаем любую ошибку БД конфликтом пользователя и не возвращаем успешный ответ при неудачной записи.
- Не передаём клиенту SQL, адрес подключения, пароль БД и подробности исключения. Не включаем хеш пароля в публичные данные пользователя.
- Для списков используем ограничение количества результатов и явную сортировку. Для истории сообщений учитываем порядок по времени и идентификатору. Не загружаем всю таблицу ради одной записи и избегаем отдельного запроса в каждой итерации цикла.
- Изменения схемы оформляем миграциями Alembic в `backend/migrations`. Индексы добавляем под реальные условия поиска и сортировки.
- Сессию закрывает `get_db` через контекстный менеджер. Заимствованную сессию не закрываем во вспомогательной функции.

### 5. Что проверяем на code review по варианту 1

- [ ] Форматирование и типы соответствуют правилам проекта.
- [ ] Условия читаются однозначно; отсутствие значения, пустая строка и ноль различаются там, где это нужно.
- [ ] Обязательные действия не зависят от короткого замыкания.
- [ ] Общая логика не дублируется, а выбранное решение не усложнено без причины.
- [ ] Запросы параметризованы, объём выборки ограничен там, где нужен список.
- [ ] Транзакции, откат и закрытие сессии имеют понятного владельца.
- [ ] Ограничения БД и ошибки записи учтены, служебные данные не раскрываются.

## Вариант 2. Имена, модули, SOLID и работа с API

Эти правила используем в нашем проекте на Python, FastAPI, TypeScript и React. Главное — чтобы другой участник мог понять код и продолжить работу.

### 1. Понятные имена

По имени должно быть понятно, для чего нужна переменная, функция или класс.

- Пишем имена на английском, без транслита.
- Не используем `data1`, `abc`, `func`, если можно назвать точнее.
- Допустимы понятные сокращения: `id`, `db`, `url`, `api`.
- Одну сущность называем одинаково в разных частях проекта.
- Функцию называем по действию: `create_user`, `verify_password`.

Пример:

```python
# Непонятно, какие данные проверяются.
def check(a, b):
    ...

# Название и аргументы объясняют назначение.
def verify_password(password, password_hash):
    ...
```

Принятые форматы:

| Что называем | Python | TypeScript |
|---|---|---|
| Переменная | `current_user` | `currentUser` |
| Функция | `create_user` | `createUser` |
| Класс или тип | `UserPublic` | `User` |
| Константа | `MAX_SEARCH_LIMIT` | `MAX_SEARCH_LIMIT` |

React-компоненты называем с большой буквы: `Input`, `AuthPage`, `ProfilePage`.

Поля JSON сохраняем по контракту сервера: `access_token`, `display_name`. Не меняем их название только на клиенте.

Правила именования Python основаны на [PEP 8](https://peps.python.org/pep-0008/#naming-conventions).

### 2. Разделение на модули

Связанный код храним рядом, разные задачи не складываем в одну большую функцию.

В нашем проекте:

| Файл | Что в нём находится |
|---|---|
| `main.py` | Создание приложения, подключение маршрутов и общие ошибки |
| `config.py` | Настройки |
| `db.py` | Подключение к БД и получение сессии |
| `models.py` | Модели таблиц |
| `users.py` | Проверка данных и операции с пользователями |
| `security.py` | Хеширование и JWT |
| `auth.py` | Маршруты авторизации и проверка сессии |
| `api.ts` | Общие HTTP-запросы |
| `App.tsx` | Маршруты и состояние пользователя |
| `pages.tsx` | Формы и страницы |
| `components.tsx` | Общие элементы интерфейса |

Основные правила:

- `Input` показывает поле, но не отправляет запросы.
- Хеширование пароля не подключается к БД.
- Настройки не зависят от HTTP-маршрутов.
- Не допускаем циклических импортов.
- Не копируем одну операцию в несколько файлов.
- Не создаём отдельный класс или слой без понятной причины.

Перед изменением общей функции проверяем, кто её вызывает. Если меняются аргументы или результат, предупреждаем остальных.

### 3. Принципы SOLID

Используем эти принципы там, где они помогают. Не добавляем наследование и сложные классы только ради соблюдения названия.

#### S — одна ответственность

У класса должна быть одна связанная область работы и понятная причина изменения.

Например, класс настроек хранит настройки, но не создаёт пользователей. Компонент поля отображает ввод, а форма управляет отправкой.

Это соответствует идее [Single Responsibility Principle](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html).

#### O — возможность расширения

Новое поведение стараемся добавлять через предусмотренные аргументы или свойства.

Например, `Button` получает `onClick`. Для каждой новой страницы не нужно дописывать условия внутри кнопки.

Исправлять существующий код можно. Заранее создавать все возможные расширения не требуется.

#### L — сохранение поведения при замене

Если одна реализация заменяет другую, она должна соблюдать тот же контракт.

Например, функция поиска возвращает пользователя либо `None`. Другая реализация не должна вместо этого возвращать строку `"не найден"`.

Это важно и для тестовых замен: они должны правильно воспроизводить нужное поведение зависимости.

#### I — только нужный интерфейс

Компонент или класс должен получать только то, что ему нужно.

Например, профилю достаточно пользователя:

```ts
type ProfilePageProps = {
  user: User | null
}
```

Не передаём ему настройки БД, обработчики регистрации и остальные данные приложения.

Типы и интерфейсы помогают описать такие договорённости. См. [документацию TypeScript](https://www.typescriptlang.org/docs/handbook/interfaces.html).

#### D — зависимости через понятные контракты

Основная логика должна зависеть от согласованных возможностей, а не от случайных деталей реализации.

Нужные зависимости передаём явно. Например, обработчик получает сессию БД через `get_db`, а не создаёт новое подключение самостоятельно.

```python
def ready(db: Session = Depends(get_db)):
    ...
```

Так зависимость удобнее менять и подменять в тестах. Сам по себе `Depends` ещё не означает полное соблюдение DIP, но помогает организовать передачу зависимостей.

Механизм описан в [документации FastAPI](https://fastapi.tiangolo.com/tutorial/dependencies/).

### 4. Внешние API и сервисы

Для клиента наш backend — отдельный HTTP-сервис. При подключении других сервисов используем те же правила.

#### Сначала согласуем контракт

До написания запроса определяем:

- адрес и HTTP-метод;
- поля запроса;
- успешный ответ;
- ошибки;
- способ авторизации.

Например:

```text
POST /auth/login
Запрос: identity, password.
Успех: 200, токен и пользователь.
Ошибки: 400 или 401.
```

Если контракт меняется, согласуем это с тем, кто использует API.

#### Запросы выполняем одинаково

На клиенте используем общий `request` из `api.ts`.

Он добавляет `/api`, заголовки и Bearer-токен, проверяет статус и обрабатывает ошибки. Не копируем эту логику в каждую форму.

- Адреса окружения выносим в настройки.
- Секреты не записываем в исходники.
- Проверяем статус ответа до использования данных.
- При `204` не пытаемся прочитать JSON.
- Запись `as User` сама по себе не проверяет полученные данные.

#### Обрабатываем ошибки

Различаем ошибку сети, HTTP-ошибку, неправильный ответ и отмену запроса.

- Пользователю показываем понятное сообщение.
- Не выдаём ошибку за успешный результат.
- Предусматриваем ограничение ожидания и отмену, где это нужно.
- Не повторяем изменяющие запросы автоматически без проверки: сервер мог уже выполнить действие.
- Отмена запроса не должна выглядеть как ошибка соединения.

#### Не раскрываем данные

- Пароли и токены не передаём в URL.
- Не записываем их в журнал.
- Токен отправляем только предназначенному сервису.
- Для удалённого сервиса с учётными данными используем HTTPS.

- [ ] Имена понятны без объяснения автора.
- [ ] Код разделён по назначению.
- [ ] Нет лишних классов, посредников и циклических импортов.
- [ ] Контракты функций и компонентов соблюдаются.
- [ ] Зависимости передаются понятно.
- [ ] API соответствует договорённостям команды.
- [ ] Успешные ответы и ошибки обработаны.
- [ ] Секреты не раскрываются.
- [ ] Проверены успешный и ошибочный сценарии.
