## Вариант 6. Ошибки, библиотеки, паттерны и Git

Эти правила используем в нашем проекте на Python, FastAPI, TypeScript и React. Главное — чтобы ошибки обрабатывались предсказуемо, архитектуру было удобно менять, а историю работы можно было проследить в Git.

### 1. Обработка ошибок и исключений

Ошибку обрабатываем там, где можем исправить ситуацию или преобразовать её в понятный ответ. Не скрываем сбой и не выдаём его за успешный результат.

- Перехватываем конкретные исключения, которые ожидаем от операции.
- Не используем пустой `except` и конструкции `except Exception: pass`.
- Ограничиваем блок `try` операциями, для которых предусмотрена обработка.
- Если восстановиться нельзя, передаём исключение выше. При замене исключения в Python сохраняем причину через `raise ... from exc`.
- Общий обработчик неожиданных ошибок размещаем на границе приложения. На сервере он возвращает безопасный ответ с кодом 500.
- Файлы открываем через `with`, а сессии БД освобождаем через предусмотренный механизм зависимости.
- После неудачной записи откатываем транзакцию перед повторным использованием сессии.

Пример обработки недоступности БД из `main.py`:

```python
try:
    db.execute(text("SELECT 1"))
except SQLAlchemyError:
    return JSONResponse(
        status_code=503,
        content={"status": "unavailable"},
    )
```

Здесь ожидаем ошибку работы с БД и возвращаем состояние недоступности. Ошибки программирования не маскируем таким ответом.

#### Ответы API

Используем согласованные статусы и формат ошибки. Для обычных ошибок API в проекте применяется структура:

```json
{
  "error": {
    "code": "internal_error",
    "message": "Internal server error"
  }
}
```

Технические проверки состояния, например `/ready`, могут иметь отдельный контракт.

| Ситуация | HTTP-статус |
|---|---|
| Неверные данные в маршрутах авторизации и пользователей | 400 |
| Отсутствует или недействительна авторизация | 401 |
| Недостаточно прав | 403 |
| Ресурс не найден | 404 |
| Конфликт данных, например занятый логин | 409 |
| Ошибка валидации остальных маршрутов по текущему обработчику | 422 |
| Неожиданная ошибка сервера | 500 |
| БД недоступна при проверке готовности | 503 |

Статус выбираем по контракту конкретного маршрута. Не возвращаем 200 с сообщением об ошибке.

#### Клиент и журналирование

- Для обычных запросов используем общий `request` из `api.ts` и класс `ApiError`.
- Различаем отсутствие соединения, ошибку HTTP и некорректный ответ сервера.
- В `catch` проверяем тип ошибки перед обращением к её свойствам.
- Пользователю показываем понятное сообщение и сохраняем возможность исправить ввод или повторить действие.
- Состояние отправки сбрасываем через `finally`, чтобы форма не оставалась заблокированной после сбоя.
- Отмену запроса обрабатываем отдельно от сетевой ошибки, если операция поддерживает отмену.
- Не повторяем изменяющие запросы автоматически: сервер мог уже выполнить действие.
- В журнал записываем сведения для диагностики без паролей, токенов и содержимого личных сообщений.
- Не отправляем клиенту трассировку стека, SQL-запросы и внутренние настройки сервера.

Проверяем успешный сценарий, ожидаемую ошибку и недоступность зависимости.

### 2. Стандартные библиотеки и инструменты разработки

Сначала проверяем возможности стандартной библиотеки и уже подключённых средств проекта. Новую зависимость добавляем, если она решает конкретную задачу лучше существующих средств.

| Задача | Что используем |
|---|---|
| Пути к файлам в Python | `pathlib` |
| Чтение и запись JSON в Python | `json` |
| Журналирование на сервере | `logging` |
| Работа со временем в Python | `datetime`, для серверных отметок времени — UTC |
| HTTP-запросы в браузере | `fetch`, обёрнутый общим API-кодом |
| Описание и проверка входных данных | Средства FastAPI и Pydantic |
| Работа с БД и миграциями | SQLAlchemy и Alembic |
| Проверки backend | pytest |
| Проверки frontend | TypeScript, ESLint, Vitest и Playwright |

Это стандартные средства платформ и зависимости проекта. Не называем FastAPI, React или SQLAlchemy частью стандартной библиотеки языка.

Основные правила:

- Не пишем собственные аналоги JSON-парсера, маршрутизатора или библиотеки JWT.
- Для паролей и токенов используем предназначенные для этого проверенные средства. Не придумываем алгоритмы шифрования и хеширования.
- Перед добавлением пакета проверяем назначение, совместимость и лицензию, обсуждаем необходимость с командой.
- Python-зависимости указываем в `backend/requirements.txt`, клиентские — в `frontend/package.json`.
- При изменении клиентских зависимостей сохраняем обновлённый `package-lock.json`.
- Backend запускаем в виртуальном окружении. Не добавляем `.venv` и `node_modules` в Git.
- Соблюдаем настройки TypeScript и ESLint проекта. Не отключаем проверку для всего файла ради одной ошибки.

Перед передачей изменений на review выполняем проверки, относящиеся к задаче.

Для backend, из каталога `backend`, в активированном окружении:

```powershell
python -m pytest
```

Для frontend, из каталога `frontend`:

```powershell
npm run lint
npm run test
npm run build
```

Если затронут пользовательский сценарий, дополнительно запускаем `npm run test:e2e` с подготовленным окружением. В pull request указываем фактические результаты и проверки, которые не удалось выполнить.

### 3. Паттерны проектирования

Применяем паттерн, когда он упрощает конкретную задачу: убирает повторение, отделяет инфраструктуру или позволяет заменить зависимость. Не создаём дополнительные классы только ради названия паттерна.

#### Передача зависимостей

Обработчик получает сессию БД через `Depends(get_db)`, а не создаёт подключение самостоятельно:

```python
def ready(db: Session = Depends(get_db)):
    ...
```

Так управление сессией остаётся в одном месте, а зависимость можно подменить в тесте. Не создаём отдельную сессию для каждой вспомогательной операции внутри одного запроса без необходимости.

#### Фасад для запросов

Общий `request` в `api.ts` служит единым входом для обычных HTTP-запросов. Он скрывает повторяющиеся детали: префикс адреса, заголовки, передачу токена и проверку статуса.

Страница вызывает эту функцию и обрабатывает результат. При изменении способа авторизации исправляем общий API-код, а не каждую форму.

#### Репозиторий при усложнении работы с данными

Если запросы к БД начинают повторяться в разных сценариях, выделяем операции хранения в репозиторий. Проверки бизнес-правил оставляем в логике сценария, а HTTP-статусы — на уровне API.

Например, репозиторий ищет пользователя по логину, логика регистрации проверяет допустимость создания, а маршрут формирует ответ клиенту.

Для небольшого набора функций в `users.py` отдельный класс не обязателен. Репозиторий вводим при реальной необходимости, сохраняя контракт: поиск возвращает пользователя либо `None`.

Перед применением паттерна проверяем:

- Какую проблему он решает сейчас?
- Какие детали можно заменить без изменения вызывающего кода?
- Стало ли проще читать и проверять поведение?

Если новый слой только передаёт те же аргументы дальше и не даёт полезного разделения, не добавляем его.

### 4. Управление версиями с Git

Соблюдаем процесс из `.docs/workflow.md`: ветка задачи → понятный commit → push → pull request → review другого участника → CI → merge.

В проекте `main` используется для демонстрационной версии, `develop` — для интеграции, а `release/0.1.0` — для кандидата релиза. Рабочую ветку создаём от согласованной командой базы.

Основные правила:

- Одну задачу выполняем в отдельной ветке с понятным названием: `feature/profile`, `fix/login-error`, `docs/code-style-sedov`.
- Перед работой проверяем текущую ветку и локальные изменения через `git status`.
- Коммит содержит одно логически завершённое изменение. Не смешиваем исправление ошибки с посторонним форматированием.
- Сообщение объясняет результат: `fix: обработать недоступность сервера при входе`.
- Перед добавлением файлов проверяем `git diff`, перед коммитом — `git diff --staged`.
- Добавляем нужные файлы явно, чтобы случайно не включить чужие изменения.
- Не коммитим `.env`, пароли, ключи, токены, локальные БД и результаты сборки. Для настроек оставляем безопасный `.env.example`.
- Не переписываем историю общих веток и не используем принудительный push без согласования с участниками.

Пример подготовки коммита с правилами:

```powershell
git status
git diff -- CODE_STYLE_SEDOV.md
git add CODE_STYLE_SEDOV.md
git diff --staged
git commit -m "docs: добавить правила для варианта 6"
```

Это пример команд; коммит выполняет участник после проверки изменений.

#### Pull request и конфликты

В pull request описываем задачу, результат и выполненные проверки. При изменении API отдельно указываем изменения контракта и связанные правки клиента.

Перед слиянием получаем review другого участника и проверяем результаты CI. Замечания исправляем в той же ветке.

При конфликте читаем обе версии и сохраняем нужное поведение. Не выбираем всю свою или чужую версию автоматически. После разрешения удаляем маркеры конфликта, просматриваем diff и повторяем затронутые проверки.

### 5. Что проверяем на code review

- [ ] Ожидаемые исключения обработаны конкретно, ошибки не скрываются.
- [ ] Статусы и формат ошибок соответствуют контракту API.
- [ ] Пользователь получает понятное сообщение, форма восстанавливается после сбоя.
- [ ] Транзакции и ресурсы корректно завершаются при ошибке.
- [ ] Пароли, токены и внутренние сведения не попадают в ответы и журналы.
- [ ] Используются стандартные средства и существующие зависимости проекта.
- [ ] Новые зависимости обоснованы и внесены в соответствующие файлы.
- [ ] Паттерны решают конкретную задачу и не создают лишние слои.
- [ ] Коммиты связаны с задачей и не содержат секретов или посторонних файлов.
- [ ] В pull request указаны результаты проверок, получено review и проверен CI перед слиянием.

В замечании указываем место, проблему и предложение по исправлению. Эти правила используем при разработке и обсуждении изменений.
